## Purpose

Run one bounded experiment that converts the strongest CLI-Anything lessons into a S.P.A.R.K.-owned reusable Rust contract candidate and exercises that contract against a real external application without granting broad shell or desktop authority.

## Experiment shape

Two pieces are evaluated together:

1. **Rust Tool Contract v0** — a typed, inspectable declaration of what a tool is allowed to accept, return, inspect, mutate, access, and prove.
2. **Blender shadow adapter** — a non-canonical adapter that drives the real Blender backend in a sandbox for one read-only inspection path and one bounded preview-render path.

## Contract v0 candidate fields

The experiment should test whether these fields are sufficient and useful; it must not promote them to a standard merely by implementing them.

- tool identity and semantic version;
- source/provenance and content/build fingerprint;
- purpose and short capability description;
- typed input schema;
- typed output schema;
- effect class: read-only / mutating / destructive / external communication;
- idempotency/retry semantics;
- required host capabilities;
- filesystem scopes: exact readable and writable roots/files;
- network scopes: default none, explicit destinations if ever needed;
- process/subprocess scope: exact allowed executable/backend;
- credential requirements: default none;
- timeout, memory, output-size, and artifact budgets;
- inspection/preflight operation;
- execution operation(s);
- error envelope and recovery hints;
- verification method and evidence requirements;
- output compression/summary contract;
- audit/provenance fields;
- sandbox profile identifier;
- transport bindings, if any (native/MCP/CLI/etc.);
- qualification status/version.

## Blender shadow-adapter bounds

Allowed experiment behavior:

- identify the exact Blender binary/version;
- inspect a controlled test scene through the real Blender backend;
- return compact structured scene metadata;
- generate exactly one bounded headless preview render through Blender;
- emit a compact verified artifact/result bundle with hashes and provenance;
- write only to experiment-owned temporary/output locations;
- record all effects and the exact backend command/admission record.

Explicitly out of scope:

- canonical S.W.A.R.M. tool-registry integration;
- canonical G.A.M.E. asset writes;
- arbitrary shell command execution;
- arbitrary Python supplied by an agent;
- self-install/update behavior;
- network access;
- credentials;
- broad home-directory access;
- background persistence;
- GUI automation;
- deployment or activation.

## Required negative tests

The prototype should prove rejection of at least:

- paths outside granted input/output roots;
- unexpected executable/backend substitution;
- undeclared network activity;
- undeclared output locations;
- malformed/oversize input;
- effect-class mismatch;
- stale or mismatched tool/backend fingerprint where verification requires a pin;
- output that cannot be verified as the declared artifact type.

## Success criteria

The experiment is successful only if all of the following hold:

1. Rust contract parses/validates deterministically.
2. Tool identity/version/provenance are explicit.
3. Read-only scene inspection works through the real Blender backend.
4. The preview is generated by the real Blender backend, not a substitute renderer.
5. The result bundle is compact, machine-readable, hashed, and independently verifiable.
6. Denied filesystem/network/process cases fail closed.
7. Errors use a stable structured envelope.
8. The adapter needs no general shell privilege.
9. The experiment produces enough evidence to decide whether the contract model should be refined, rejected, or advanced.

## Research inputs to revisit before implementation

- CLI-Anything contract, skill, test, and preview-bundle patterns;
- official MCP Rust SDK (`rmcp`) schema/transport mapping;
- ToolHive runtime/registry/gateway permission profiles;
- Goose layered tool-security inspectors;
- Wasmtime + WASI + cap-std vs Extism for containment;
- MCP Inspector for independent surface qualification;
- ACP only if the prototype needs an MCI/client-facing session binding.

## Decision after experiment

The experiment should end in one of:

- reject the contract shape;
- revise and repeat in the sandbox;
- retain as experimental only;
- propose a separate, reviewable S.W.A.R.M. tool-contract standard;
- propose one narrowly scoped production adapter.

No promotion is automatic.
