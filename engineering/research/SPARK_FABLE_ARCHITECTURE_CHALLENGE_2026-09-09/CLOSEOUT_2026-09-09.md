## What the checks establish

The executable checks establish deterministic causal records/digests across tested budgets,
chunk sizes, and catch-up partitions; stable scheduler extraction; per-WorkKey atomicity in
the research setting; payload-sensitive hashing; typed missing/corrupt-body rejection;
deterministic overflow rejection without partial writes; one-active-request flow control;
retained result redelivery; sequence-based GAME deduplication in the model; and explicit
refusal of old or duplicate requests. They also establish that delivery chunk boundaries do
not alter the modeled causal result.

They do **not** establish byte-compatible snapshots, transport/concurrency behavior, durable
mailbox recovery, a real process-crash boundary, production throughput, wall-clock bounds,
or the scope of a general memory guarantee. Pass 3's restart check clones and drops an
in-memory device. The example substitutes a command log for Phase-1 `TimelineIngress` and
assumes the host durably re-presents a paused mailbox head. `engine.trace` remains unbounded
and consumed payload bodies remain retained. A transaction-count budget is not a wall-time
budget. The proposed per-WorkKey transaction unit, strict late-input rule, one-profile-per-
engine choice, and other architectural changes remain proposals for Operator decision.

## Architecture conclusion

Fable recommends retaining Phase 1 and extending it rather than rewriting the engine. The
proposed integration is one outstanding request: GAME pulls bounded result chunks; Spark
returns `Busy` while occupied; and Spark retains a result until GAME acknowledges it. The
Operator clarified that Q/FIFO/mailboxes are optional mechanisms; controlled throughput and
reliable handling are the requirements. This research completion does not close production
architecture gates or authorize implementation.

### Acknowledgment gap and recovery contract

`acked_through` or another persisted sequence number alone cannot prove exactly-once
application. GAME must atomically make the result's effects visible and record the application
identity (for example `(spark_instance_id, report_seq, report_digest)`), or the application
must be idempotent under that identity. Only after that atomic commit may GAME acknowledge.

The replay contract must specify: Spark retains an unacknowledged report and redelivers the
same sequence/digest; GAME deduplicates an already-committed identity; Spark treats a matching
ack as release; and mismatches are fatal/refused rather than silently advancing. If Spark has
durably committed a report but GAME has not recorded application, GAME replays and applies.
If GAME recorded application but Spark did not record the ack, replay is a no-op and GAME
re-acknowledges. If Spark restored before the report commit while GAME restored after applying,
GAME must not silently accept a new divergent report: the identities/digests require a
reconciliation or operator-visible refusal. Conversely, if Spark retains a report that GAME
restored without its application record, GAME applies it once. These are atomicity and replay
assumptions to test, not guarantees delivered by this research model.
